#### A.3.2 Les trois types — comment chacun fonctionne concrètement

Verbatim `docs/pedagogy.md` §2 :

| Type | Compteur | Le starter… | Les tests vérifient… | Prépare à… |
|---|---|---|---|---|
| `creation` | 001-099 | signatures + `...`/`NotImplementedError` + docstring contrat | comportement attendu | écrire from scratch |
| `modification` | 101-199 | code **qui marche mais imparfait** | comportement **préservé** ET refactor **appliqué** (`ast`/mypy) | PR open-source : améliorer sans casser |
| `debugging` | 201-299 | code **cassé**, tests rouges au départ | comportement corrigé, edge case géré | lire stack trace, fix chirurgical |

Ratio cible **par chapitre** : 50 % creation / 30 % modification / 20 % debugging.

**Exemple `creation`** — `ch01-001` starter (verbatim) :

```python
"""Une entreprise de meubles veut des objets lisibles dans ses logs.

Implémente la classe `Chair` :
- `__init__(self, ref: str, price: int)` stocke `ref` et `price`.
- `__repr__` renvoie EXACTEMENT : Chair(ref='A1', price=99)
  (guillemets autour de la ref, pas autour du prix).
"""


class Chair:
    def __init__(self, ref: str, price: int) -> None:
        ...

    def __repr__(self) -> str:
        ...
```

Solution (verbatim) :

```python
"""Choix de design :
- __repr__ utilise !r (repr) sur ref pour les guillemets gratuits et corrects
  même si la ref contient une apostrophe — plus robuste qu'un f-string manuel.
- price est un int : pas de !r, on veut 99 et non '99'.
"""


class Chair:
    def __init__(self, ref: str, price: int) -> None:
        self.ref = ref
        self.price = price

    def __repr__(self) -> str:
        return f"Chair(ref={self.ref!r}, price={self.price})"
```

Tests (5 cas, dont un edge — verbatim `ch01-001/tests.py`) :

```python
from solution_user import Chair

def test_init_stores_attributes(): ...
def test_repr_exact_format(): ...
def test_repr_quotes_ref_not_price(): ...
def test_repr_returns_str(): ...
def test_repr_handles_ref_with_apostrophe():
    # edge case : une ref exotique ne doit pas casser le repr
    assert repr(Chair("O'1", 10)) == 'Chair(ref="O\'1", price=10)'
```

**Exemple `modification`** — `ch01-101-furniture-kill-getters` starter (verbatim) :

```python
"""Ce code marche mais n'est pas pythonique : getters triviaux, pas de __repr__.

Refactor :
1. Supprime get_ref et get_price ; expose `ref` et `price` directement.
2. Ajoute __repr__ -> Chair(ref='A1', price=99).
3. Ne casse aucun comportement (les valeurs restent accessibles).
"""


class Chair:
    def __init__(self, ref, price):
        self.ref = ref
        self.price = price

    def get_ref(self): return self.ref
    def get_price(self): return self.price
```

#### A.3.3 Exécution + vérification + feedback

**Exécution du code utilisateur — exact (`web/lib/pyodide.ts`).**

1. **Pyodide est chargé une seule fois** par session (singleton `pyodidePromise`, ligne 11). Phases exposées : `idle → pyodide → pytest → ready` (callback `onPhase`, lignes 30-46). Le script `pyodide.js` est injecté depuis CDN jsdelivr (CSP-vulnérable si l'utilisateur passe par un proxy bloquant — non géré).
2. `loadPackage("micropip")` puis `micropip.install("pytest")` (lignes 40-42). Donc à la première session : un download Pyodide (~6 Mo en .wasm + .data) + pip install pytest. **Aucun fallback hors ligne** — sans réseau, l'app est inutilisable.
3. **Préchauffe** au montage du Workbench : `useEffect(() => { getPyodide(setPhase) })` (`ExerciseWorkbench.tsx:52-54`). L'utilisateur peut lire l'énoncé pendant que Pyodide charge.

**Deux modes** :

- **`Run`** (`runCode(userCode)`, lignes 121-141) : `exec()` du code dans un sandbox Pyodide, redirection stdout+stderr, traceback Python si exception. **Ne lance pas les tests**. Pratique pour des `print()` exploratoires. Si pas de print : message « *(aucune sortie — ton code ne print rien)* ».
- **`Submit`** (`runTests(userCode, testsCode)`, ligne 111-118) : c'est le **vrai juge**.

**Le juge — `PYTEST_HARNESS`** (verbatim `pyodide.ts:62-109`, condensé) :

```python
for _m in ("solution_user", "tests"):
    sys.modules.pop(_m, None)            # repart d'un état propre à chaque submit
if "/exo" not in sys.path:
    sys.path.insert(0, "/exo")

import pytest

class _Collector:
    def pytest_runtest_logreport(self, report):
        nid = report.nodeid
        if report.when == "call": self.reports[nid] = report
        elif report.outcome == "failed" and nid not in self.reports:
            self.reports[nid] = report   # erreur en setup (import bugué)

_buf = io.StringIO()
with contextlib.redirect_stdout(_buf), contextlib.redirect_stderr(_buf):
    _code = pytest.main(
        ["-q", "-p", "no:cacheprovider", "--no-header", "/exo/tests.py"],
        plugins=[_c],
    )

# JSON.dumps({"ok": ..., "tests": [{"name", "outcome", "message"}], "stdout": tail(4000)})
```

Le flux : code user écrit dans `/exo/solution_user.py`, `tests.py` copié
dans `/exo/tests.py`, `pytest.main` lancé, un plugin collector capture les
rapports par test, payload JSON renvoyé au JS. `tests.py` importe **toujours**
depuis `solution_user`. Convention `exercise-format.md` §7 : « Le validator
charge tour à tour `solution.py` puis `starter.py` sous ce nom. »

**Rendu du feedback** — `web/components/TestResults.tsx` :

- Bandeau vert / rouge avec score `passed/total` (« Tout vert — 5/5 ✅ » ou « 3/5 tests passent »).
- Liste de `<Row>` cliquables : `✓` vert ou `✗` rouge + nodeid pytest tronqué (`test_repr_handles_ref_with_apostrophe`).
- Sur un échec, **expandable** : pretty-print du `longreprtext` pytest (tronqué aux 1 600 derniers caractères côté Python, ligne 91-94). Donc l'utilisateur voit `assert "DESK-204"` etc. — bonne lisibilité.
- Cas pathologique : `report.tests.length === 0` → affichage brut du `stdout` (« Aucun test collecté (erreur d'import ?). »).

**Solution gated, hints progressifs.**

- `HintsPanel.tsx` : `shown` state local, 0 par défaut. Bouton « Révéler un indice » qui incrémente. Pas de persistance entre sessions.
- Solution gated (`ExerciseWorkbench.tsx:115`) : `canSeeSolution = done || fails >= 3`. Avant ça, bouton désabled avec tooltip « Disponible après réussite ou 3 tentatives échouées ». Affichage = `DiffSolution` ligne-à-ligne sur les trim, divergences en rouge gauche/vert droite.

**Validation côté Git (`tools/validate_*.py`).** Avant tout commit
touchant `exercises/` (cf. `CLAUDE.md` §6), `tools/validate_all.py` parcourt
le repo et applique à chaque exo (`validate_exercise.py`) :

1. présence des 4 fichiers (`meta.yaml`, `starter.py`, `solution.py`, `tests.py`) ;
2. parsing YAML + 14 champs présents + contraintes du schéma ci-dessus ;
3. cohérence id ↔ chemin (chapitre/type/dossier) ;
4. **solution.py chargée comme `solution_user` → pytest doit passer 100 % vert** (sinon exo bugué) ;
5. **starter.py chargé comme `solution_user` → pytest doit échouer** (sinon le starter contient déjà la solution / pas de bug / refactor déjà fait).

Timeout filet de **20 s** (`validate_exercise.py:119`) : un starter buggé
qui boucle (`__getitem__` qui ne lève jamais `IndexError`) est traité
comme « échoue », comportement souhaité. Logs flushés `print(..., flush=True)`
pour streaming en CI.

**Auto-évaluation par IA dans la webapp : non, jamais.** `CLAUDE.md` §2 bannit
explicitement : « **IA d'éval dans la webapp** (les tests pytest tranchent,
point) ». Le juge unique = pytest.

### A.6 UX / visuel

**Design system.** Tokens custom Tailwind v4 (variables CSS) référencés dans
les composants : `background`, `foreground`, `surface`, `surface-2`,
`border`, `muted`, `accent`, `ok`, `fail`. Palette minimaliste sombre,
avec accents bleu (~`#7c9cff`), vert pour `ok`/`passed`, rouge pour `fail`.
Polices Geist Sans + Geist Mono (`web/app/layout.tsx:5-6`).

**Ressenti.** Aucun fioriture visuelle hors confetti à la première
réussite (`Confetti.tsx` : 90 particules `<canvas>`, fade en ~1,5 s,
zéro dep). Layout dense et sobre, ergonomie « workbench » (énoncé gauche
/ éditeur droit). Header de Workbench affiche le tableau de bord en chips
(type, difficulté, thème, concepts).

**Responsive.** Confirmé en code, deux modes :

- **mobile (`< lg`)** : énoncé empilé sur l'éditeur sur l'éditeur sur les résultats. Boutons taille XL (`px-3 py-2`) + `touch-manipulation` pour tap-targets confortables (cf. commit `f059e99 phase 4 polish`).
- **desktop (`lg`)** : grille 2 colonnes plein écran (`lg:grid-cols-2 lg:h-screen lg:overflow-hidden`), panneaux indépendamment scrollables.

**Points UX particuliers** :

- Préchauffe Pyodide silencieuse à l'ouverture d'un exo : l'utilisateur lit l'énoncé pendant que ~6 Mo se chargent.
- État `phase` affiché en discret à droite du header (« Chargement de Python (Pyodide)… » / « Installation de pytest… » / « Prêt »).
- Confetti déclenché **uniquement à la première réussite** (`if (!done) setBurst(b => b + 1)` ligne 84) — pas de spam si on resoumet un exo déjà vert.
- Bouton Reset par exo demande `confirm()` **seulement** si l'exo est déjà complété (`ExerciseWorkbench.tsx:103-104`).
- `ResetAllButton` n'apparaît sur la home que si ≥ 1 exo complété (`ResetAllButton.tsx:13`).
- **Latence perçue de navigation** : flagué par l'utilisateur (`MEMORY.md` → `webapp_nav_latency.md`). Passe 1 : lazy-load Monaco + mémoïsation `getAllExercises` (commits `f059e99` et `c8eb05c`). À revérifier sur build prod.

**Limites UX observées** :

- Aucun moteur de **recherche** d'exo.
- Aucun **filtre** par difficulté / type / thème / concept dans la liste d'un chapitre.
- Aucune **rétro-action** sur le rythme : pas de chrono, pas de streak, pas de courbe.
- Aucune mention du **niveau de difficulté** dans le bandeau de réussite (juste « Tout vert ✅ »).
- Pas d'**historique** des tentatives (combien de fois on a échoué avant de réussir, quelle solution on avait collée).
- Pas d'**export** de progression ni de partage social (volontaire, mais à noter).
- Pas de **a11y** validée (lecteur d'écran, focus management du modal solution, contrastes).

### TOP 5 améliorations à plus fort impact, tous objectifs confondus

> Tri par ROI absolu sur la cible *ML Inference Engineer / Mistral déc 2027*,
> qui reste le centre de gravité de ce repo (`CLAUDE.md` §1).

1. **M1 — Seed ch6-ch9 (mutability · functions · type hints · decorators).** [Effort L · Prio P0]
   *Pourquoi* : tier S quatre fois, couverture du contrat triple (de 21 % à 38 %), débloque toute la partie *expert Python* — sans ces 4 chapitres seedés, Pipithon reste un dojo de débutant idiomatique. C'est le chemin critique direct vers les Couches 1, 9, 14 du mapping.

2. **M3 — Définir un mini-framework PyMistral interne au repo et lui adosser les exos ch ≥ 8.** [Effort L · Prio P0]
   *Pourquoi* : aujourd'hui, `pymistral_link: null` partout. Tant que le framework n'existe pas, les exos ch ≥ 8 utiliseront des thèmes ML *fake* sans cohérence. Un mini-framework interne (5-7 classes Python pures) donne **une narrative bout-en-bout** : « j'ai construit mon `KVCache` au ch11, je l'ai itéré au ch17, je l'ai exposé en async au ch21 ». C'est la différence entre 100 exos déconnectés et un projet de portfolio défendable en entretien.

3. **O1 — Nouveau type d'exo `review` (lire un diff, répondre à 4-6 questions).** [Effort L · Prio P0]
   *Pourquoi* : `mapping-mistral.md` Couche 16 est explicite — « cette couche n'est pas optionnelle ». Le format `creation/modification/debugging` actuel rate complètement la **lecture** de code (toujours écrire/réparer). Un type `review` est un multiplicateur d'effet pour tout futur contenu OSS (vLLM, SGLang, transformers).

4. **M2 — Mode mypy strict pour `modification`.** [Effort M · Prio P0]
   *Pourquoi* : sans ça, les 4 chapitres seedés ci-dessus (M1) ne pourront pas drilller le type-hinting au niveau attendu Mistral. C'est un déblocage technique léger qui démultiplie l'effet de M1 et de C12.

5. **B2 — Mode `chrono` + B5 mode `closed-book`.** [Effort M+S · Prio P1]
   *Pourquoi* : utile à **deux** objectifs en même temps. Pour Mistral, c'est le test « est-ce un réflexe Pythonique ? » (anti-pattern n°1 verbatim : *« si tu ne peux pas coder de mémoire... »*). Pour le concours bot programming, c'est le pré-requis non négociable. Faible coût d'implémentation, gros effet de discipline.
